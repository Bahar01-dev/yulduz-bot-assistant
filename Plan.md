# План реализации: Telegram-бот «ИИ-агент для Instagram-контента»

> **Что это за документ.** Пошаговый план разработки бота из папки `Bot-Assistant`: фазы, задачи,
> трекинг прогресса, обработка ошибок. Источник истины по поведению — `Bot-Assistant/spec.md`;
> этот план описывает ПОРЯДОК работ и статусы. **Обновляется после каждой фазы**
> (см. раздел «Как пользоваться планом и механизм самообновления»).

---

## Контекст

**Зачем этот план.** В папке `Bot-Assistant` лежит готовая спецификация (`spec.md`, `CLAUDE.md`,
`idea.md`, `research.md`), но **кода ещё нет** — только документы. Спека подробная, но это «что делать»,
а не «в каком порядке и как отслеживать прогресс». Нужен план, по которому можно идти фазами,
видеть статус и не терять блокеры.

**Что строим.** Персональный Telegram-бот (один пользователь — владелец) для генерации
Instagram-контента в стиле владельца: посты и сценарии Reels. Модель — Claude `claude-opus-4-8`.
Память на SQLite (3 уровня), онбординг через aiogram FSM, опционально голосовой ввод (Groq Whisper),
деплой на Railway.

**Главная метрика успеха.** Готовый пост/сценарий за < 60 секунд, без необходимости переписывать.

**Что отдельно подчёркнуто в этом плане:**
1. **Обработка ошибок LLM** — если модель вернула ошибку, бот пишет пользователю понятное
   русское сообщение (никогда — технический текст/стектрейс). Технические детали уходят в stdout
   (Railway logs) + короткий алерт владельцу в Telegram.
2. **Самообновление статусов** — после каждой фазы обновляются таблица прогресса, колонка «Факт»,
   блокеры и критерии готовности.

## Как пользоваться планом и механизм самообновления

**Триггер для продолжения работы:** фраза «**Продолжи разработку по Plan.md**». Claude Code читает
сводную таблицу прогресса, находит первую незавершённую фазу и продолжает с неё.

**После завершения КАЖДОЙ фазы разработчик (Claude Code) обязан:**
1. Обновить статус фазы и её задач в таблицах (📋 → 🚧 → ✅).
2. Заполнить колонку **«Факт»** — что реально сделано, дата, отличия от плана.
3. Зафиксировать **блокеры** (если были).
4. Отметить галочками пункты **«Критерии готовности»**.
5. Добавить запись в **«Журнал изменений плана»** внизу документа.
6. Если изменилась структура/стек/ключевые решения — обновить `spec.md` и `CLAUDE.md`
   по правилу самообновления из `CLAUDE.md` (истина — в `spec.md`).

### Принципы тестирования (выбор: ручное QA)

Автотестов в MVP нет (как в `spec.md`). В каждой фазе — **чеклист ручного QA**: запуск через
`python main.py` + проверка в реальном тестовом Telegram-боте, осмотр БД через `sqlite3`.
Фаза считается готовой только когда весь её QA-чеклист пройден.

## 🛡️ Обработка ошибок LLM — сквозной слой (ключевой раздел)

**Принцип №1:** пользователь НИКОГДА не видит технический текст, стектрейс, английское сообщение
об ошибке или код HTTP. Только понятное русское сообщение и путь, что делать дальше.

**Принцип №2:** разработчик ВСЕГДА получает полную техническую информацию — тип исключения,
сообщение, traceback, контекст запроса — в stdout (Railway logs). При критических сбоях — ещё и
короткий алерт владельцу в Telegram.

**Архитектура:**
- `utils/logger.py` — настройка `logging` в stdout (формат: время, уровень, модуль, сообщение).
- `utils/errors.py`:
  - `ERROR_CATALOG` — словарь «тип ситуации → (русское сообщение, уровень лога, слать ли алерт владельцу)».
  - `safe_generate(...)` — обёртка вызова Claude: retry ×2 с экспоненциальной задержкой (≈1с, 2с),
    ловит все типы ошибок Anthropic, логирует детали, возвращает либо результат, либо
    готовое русское сообщение для пользователя.
  - `alert_owner(bot, text)` — короткое уведомление владельцу (с троттлингом/дедупом, чтобы не спамить).
- Глобальный error-handler aiogram — ловит любую необработанную ошибку (catch-all) → RU-сообщение + лог.
- Индикатор «печатает…» во время генерации; при ошибке заменяется на дружелюбное сообщение.

### Каталог ошибок (реализуется в Фазе 2, применяется везде)

| Ситуация (техническая) | Что видит пользователь (RU) | Лог в stdout | Алерт владельцу | Retry |
|---|---|---|---|---|
| Нет связи с Anthropic (`APIConnectionError`, сеть) | «Сервис временно недоступен. Попробуй ещё раз через минуту 🙏» | ERROR + traceback | да | ×2 |
| Лимит запросов (`RateLimitError`, 429) | «Слишком много запросов подряд. Подожди минутку и попробуй снова.» | WARNING | нет | нет |
| Сбой сервера ИИ (`APIStatusError` 5xx) | «Сервис ИИ временно недоступен. Попробуй чуть позже.» | ERROR | да | ×2 |
| Неверный/отсутствует ключ (`AuthenticationError`, 401) | «Бот настроен некорректно. Я уже сообщил владельцу — скоро починим.» | CRITICAL | да | нет |
| Слишком большой запрос (`BadRequestError`, 400, контекст) | «Запрос получился слишком большим. Давай короче — переформулируй, пожалуйста.» | ERROR | нет | нет |
| Таймаут генерации | «Генерация затянулась. Попробуй ещё раз — обычно помогает.» | WARNING | нет | ×1 |
| Пустой/нечитаемый ответ модели | «Не получилось собрать ответ. Нажми «🔄 Переписать» — попробую заново.» | ERROR | нет | ×1 |
| Модель отказалась / контент-фильтр | «ИИ не смог обработать эту тему. Попробуй переформулировать.» | WARNING | нет | нет |
| Ошибка Groq Whisper (голос) | «Голосовой ввод временно недоступен. Напиши текстом, пожалуйста 🙏» | WARNING | нет | ×1 |
| Ошибка записи в БД | «Не получилось сохранить. Попробуй ещё раз через секунду.» | ERROR | да | ×1 |
| Любая прочая ошибка (catch-all) | «Что-то пошло не так. Я уже разбираюсь — попробуй ещё раз чуть позже.» | ERROR + traceback | да | нет |

> Дополнительно (из `spec.md` §14): онбординг не завершён → «Нужно сначала настроить профиль. Нажми /start»;
> пустой профиль → не генерировать, вернуть в онбординг.
